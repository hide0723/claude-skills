## グレードの方針

グレード制度そのものは `role-expectations/`（31グレード・9職階の期待職能表）が正。
ここには A 人材の計画として決めた**運用方針**だけを置く。

### 1. 職階が上がらなければグレードも上がらない（帯をまたぐときのみ）

帯の中（S1→S6 など）は到達水準に応じて昇格できる。
**帯をまたぐ昇格には職階の昇格を伴う**ことを要件とする。

適用する境界：**T → S ／ SS → M ／ SM → D ／ D → P**

（S → SS の扱いは未決。業務推進課の卒業要件と直結するため要決定）

### 2. 職責の軽減ではグレードを下げない

引退・体調・介護等により職責を軽減する場合、職階を外してもグレードは据え置く。
グレードは過去の到達水準を表すものであり、職責の軽減をもって引き下げない。

- 適用例：越沼浩美（引退間近のため負担軽減。主任を外し、グレードは SS1 のまま）

### 3. 昇格要件は期待職能に振り込む

数値基準を別立てにせず、`role-expectations/levels.py` の
「期待される役割／測定指標1・2／期待されるプロセス／昇格の条件」に統合する。

### 4. 担当報酬を持たない職務の評価

業務推進課・総務・経理課は関与先の担当報酬を持たないため、測定指標2で見る。
貢献額は業務コスト台帳（`pricing/decisions.md` の市場価値の階梯）で算出する。

> **注意**：市場価値の階梯の記号（S1〜S7・P1・P2）と人事グレードの記号（S1〜S6・P1）が
> 同じ表記で別の意味になっている。混同を避けるため、階梯側の記号を変えることが望ましい。

### 5. 昇格判定に使う数値は按分後の値

Asana「担当報酬額（年額）」は**按分前**の値であり、そのまま昇格判定に使わない。
チーム内の関与・所長関与・業務推進課の関与を反映した**按分後**の値で判定する。

**按分ルールは未確定。これがグレード制度全体の律速となっている。**
